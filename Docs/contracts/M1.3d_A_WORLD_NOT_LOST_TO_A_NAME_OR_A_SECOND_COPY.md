# Contract M1.3d — A world not lost to a name or a second copy

**Status:** closed 2026-09-14, the exit record at the end; opened the same day, on William's "continue", after the bug
hunt he asked for on 2026-09-13 found two ways a world can lose a founder, or itself. Owner: Claude (Opus 5).

## What was found (2026-09-13)

- **Two names, one file.** A founder's file is named from their name with its capitals kept, and Windows sets capitals
  aside, so William and william are written to one file. The second one's bytes stand, and the first founder wakes at
  the wake with empty hands. A crash between the save's record and its files leaves a record naming a file that holds
  neither founder, and the world is refused. "Jo Jo" and "Jo_Jo" share a file on every system, and a name Windows
  keeps for a device (Con, Aux, Nul) cannot be written at all.
- **Two programs, one folder.** Nothing stops the game being opened twice on one world, or the game and a server.
  Opening a folder recovers it, and recovering deletes whatever a save has written aside. The second program deletes
  the files the first is writing, the first's record then names files that are gone, and the world is refused for good.

## What this slice promises

1. **A name too like one the world knows is refused at the door**, with both names in the reason; the name the world
   knows is still welcomed back.
2. **A save never writes two founders to one file.** It is refused before anything is written, naming both, and the
   save before it stands.
3. **A founder named for a device gets a file of their own**, written and read back.
4. **A world is held by the program that opened it.** A second program is refused, in plain words, before it reads or
   changes anything. The hold ends when the first program has written its last save, when its load fails, or when it
   dies.

## Non-goals

Names that differ only in capitals becoming one founder, which is a question of who a founder is, for the owner; other
tools copying or reading a folder while a game holds it; the other bugs the hunt found.

## How it is proved

`dotnet test`, each new test's reason broken once; the Unity-layer compile; `python Tools/unity/editmode.py`; and a
built player, run without a window, refused a world the dedicated host holds, with the reason in its log.

## Exit record (2026-09-14)

**What exists.** `WorldSave.ShareAFile` says whether two names would be written to one player file, capitals set aside
and marks made underscores. The server refuses such a name at the door, naming both, and a save refuses to write two
founders to one file before it writes anything. `WorldSave.FileNameFor` puts an underscore in front of a device's name.
`WorldLock` holds a world folder for the program that opened it: `WorldPreparation.Load` takes it before reading
anything and lets it go when the load fails, and the load's result holds it until disposed, which the game does after
its closing save and the dedicated host after its last. What a player notices: a friend who joins as william beside
William is told in words that the name is too like one the world knows, and opening a world already open in another
copy of the game, or on a server, says so on the loading screen instead of harming the world.

**Tested, and how.**

- `dotnet test`: 472 passed. A name differing from a remembered founder's only in capitals is refused, naming both, and
  so is Jo_Jo while Jo Jo is connected, where Jo Jo and William themselves are welcomed. A save of William and william is
  refused, the save before standing and nothing written aside. A founder named Con is written and read back. A world
  one load holds is refused to a second load, which leaves a file the first one's save had written aside where it was;
  once the first lets go, the world opens, that file is cleared, and nothing of the hold is left in the folder. The
  preparation tests let each world go when done with it, and those that open a world after a failed load show that a
  failed load lets it go.
- Each new test's reason was broken once, in a way that still built, the tests went red, and the code was put back: the
  door letting a clashing name in; a save writing two founders to one file; a device's name kept as a file's; the hold
  shared with a second program; a failed load keeping the hold, which reddened three of the preparation tests.
- The Unity-layer compile: 0 warnings, 0 errors. Edit-mode: 8 of 8.
- Across programs, with the built player (`Build/Player-M13d`) run without a window: while the dedicated host held
  `Artefacts/worlds/f11-controls` the folder held `world.lock`, and the game asking for the same world logged "This
  world is already open in another copy of the game or on a server" and waited at its failure screen until the run was
  stopped. The host then saved and stopped, leaving no `world.lock`, and the game, run again, opened the world, played
  twenty seconds, saved on closing in 52.1 ms and left no `world.lock`.

**Not exercised, or not holding.**

- A program killed while holding a world was not tried: that its files close with it, and the hold with them, is the
  operating system's.
- Capitals are set aside as .NET sets them aside, which differs from Windows's own file-name table for a few letters
  outside English.
- The refusal at the door names the founder the world knows to whoever asks, which on a public server tells a stranger
  a name that is in the world.
- A host on another system than Windows holds the folder with a lock only programs that ask for one respect; no other
  system was tried.
- The hunt's other bugs are untouched.

**The owner's hands.** Nothing to feel. Opening one world in two copies of the game at once now shows a message in the
second instead of putting the world at risk.
