# Contract M1.3c — A save that does not pause the game

**Status:** closed 2026-09-13, the exit record at the end; opened the same day, on William's "continue", to pay the debt M1.3b
left: the safe save flushes every file to the disk, and the game saved on its main thread. Owner: Claude (Opus 5).

## What was found (2026-09-13)

- **The safe save costs a frame or more.** The host's saves of the gate world under M1.3b took 258.7 ms, the first in a
  fresh process, then 51.9 and 32.4 ms; on the same disk five small files take a median 16.0 ms flushed against 2.1 ms
  unflushed. A frame at sixty a second is 16.7 ms.
- **The game pays for it on its main thread.** `Bootstrap` saves every thirty seconds and when the game closes by calling
  `GameServer.Save` between two frames, so the whole save, its files included, stands between one frame and the next.
- **Only the making of a save needs the main thread.** A save's bytes come from the world and the players, which the main
  thread steps; writing them aside, flushing them and putting them in place touch only those bytes and the disk.

## What this slice promises

1. **An autosave is made on the main thread and written behind it.** The game's autosave makes the save's bytes between
   two frames, and writes its files on a worker while the game goes on.
2. **One at a time.** An autosave that comes round while the last is still being written is left for the next.
3. **The save on closing is whole.** Closing the game lets a save still being written finish, then writes its own before
   the process ends; if the one being written does not finish within half a minute, none is written over it.
4. **A save written behind is the world as it stood when it was made:** nothing done to the world after the making reaches
   it, and it is byte for byte the save written in place.
5. **Measured in the built game.** A built player, run without a window, logs each autosave's time on the main thread and
   behind it, and the times are read from its log.
6. **A file another program holds for a moment is waited for** (amended 2026-09-13, once the built game's closing save had
   failed on one). A file a save or a recovery puts in place, removes or clears away while a virus scanner or an indexer
   holds it is tried again, each wait longer than the last; a save that still cannot fails naming the file, and the next
   load finishes it.

## Non-goals

The dedicated host's saves, which stay where they are, since it draws no frames; making a save's bytes cheaper; a save's
pull on the disk while the game streams tiles.

## How it is proved

`dotnet test` and the Unity-layer compile, the count as run; `python Tools/unity/editmode.py`; the built player's log.

## Exit record (2026-09-13)

**What exists.** `WorldSave.Prepare` makes a save from the world and the players as they stand and `PreparedSave.Commit`
writes it, once; `WorldSave.Write` is the two on one thread, as the host and the tests use it. The game makes each
autosave between two frames and writes it on a worker, one at a time, and closing the game waits up to half a minute for
the save being written, then writes its own; the log gives each autosave's two times and the closing save's. A file
operation of a save or a recovery that another program holds up is tried again, each wait longer than the last, then
fails naming the file (promise 6). What a player should notice: the game no longer catches for a moment every half a
minute, except perhaps at the first autosave (below). Nothing else changes.

**Tested, and how.**

- `dotnet test`: 468 passed. `SaveInterruptionTests` makes a save, moves the world on, then writes the save: it reads as
  the world when it was made. A save written on a worker is file for file and byte for byte the save written in place on
  the test's thread, and a second write of it is refused. A region file the save replaces, held open by the test without
  leave to delete it, is waited for and put in place once let go; held for good, the save fails with the file's name and
  its record placed, and once the file is let go the next read finishes the save, with nothing left over.
- Each new test's reason was broken, the tests went red, and the code was put back: a made save that forgets it was
  written, so it can be written twice (a first attempt, taking the guard out, stopped the build instead, since a field
  set and never read is an error here); a held file tried only once; a failure thrown without the file's name.
- The Unity-layer compile: 0 warnings, 0 errors. Edit-mode: 8 of 8.
- The built player, run without a window for 75 s on a world of one founder and one region file, three times, the first
  two before the retries (`Build/Player-M13c`) and the third with them (`Build/Player-M13c2`): each run's first autosave
  was made in 15.7, 17.6 and 15.4 ms on the main thread and written in 41.5, 38.6 and 41.1 ms behind it; each second
  autosave was made in 1.1, 1.1 and 1.3 ms and written in 34.4, 33.4 and 34.4 ms. The saves on closing took 35.0 and
  35.8 ms in the second and third runs, and after the third the folder held one whole save and nothing else.

**Found on the way.** In the first run the save on closing failed: Windows could not replace `regions/r.5.13.egr`, which
the autosave before it had written some fifteen seconds earlier, and the folder was left holding the save's record, two
files put in place and two still written aside. M1.3b's recovery did what it was built for: the dedicated host, loading a
copy of the folder, finished the save, and the game's second run on the folder itself did the same before it played.
Nothing in the game keeps its files open and the failure did not come again, so another program reading the new file is
the likeliest cause; promise 6 was added for it.

**Not exercised, or not holding.**

- What held the file in the first run was not caught. The retries are proved against a handle a test holds, not against a
  virus scanner or an indexer.
- The first autosave in a run takes about a frame at sixty a second to make, where later ones take about a millisecond;
  what the first pays for was not taken apart (DEBTS).
- No frame was timed. The game ran without a window, and what an autosave costs a frame is read from the log's times.
- An autosave that comes round while the last is still being written, and a closing that outwaits its half a minute, were
  not exercised: each save was written in under a tenth of a second of its thirty.
- The save on closing is still written on the main thread, as the game ends, when no frame waits for it; the dedicated
  host saves in place on its own thread, a non-goal.
- A larger world's save was not timed in the game. Its writing is behind the main thread; its making grows with the world.

**The owner's hands.** Whether the game still catches every half a minute as you walk: since M1.3b it did, and now it
should not, except perhaps once, half a minute after the world opens.
