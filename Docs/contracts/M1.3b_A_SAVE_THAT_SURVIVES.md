# Contract M1.3b — A save that survives its interruption

**Status:** closed 2026-09-13, the exit record at the end; opened the same day, after GPT-6's review, relayed by William, named `WorldSave.WriteAtomic` deleting a file
before moving its replacement in, and Claude confirmed it and found what it costs. Owner: Claude (Opus 5).

## What was found (2026-09-13)

- **A save can lose its world.** `WriteAtomic` writes a file's replacement beside it as `.part`, deletes the file, then
  moves the replacement in. A crash between the delete and the move leaves nothing under the name. For `world.json`
  that loses the world outright: `WorldSave.Exists` answers no, the game's menu no longer lists the world to continue
  (`Bootstrap.LatestWorldDir` looks for that file), and the host or the game given the folder makes a new world in it
  (`WorldPreparation.Load`), over the one the founder lived in.
- **A save is many files, written one after another:** `world.json` (the tick, the clock, the next entity's id), then
  each player's file, then each region file, then the removal of the files of cells that emptied, then `digest.txt`. A
  crash part of the way through leaves a mixture. A thing picked up since the last save can then lie in an old region
  file while a new player file carries it, and the load refuses the whole folder ("carries entity 7, which also lies in
  a region file"); a thing that crossed a cell's edge can lie in two files at once.
- **Nothing reaches the disk before it is moved into place.** A file's bytes are handed to the operating system and
  moved at once, and a power cut can leave a moved file empty.
- **Saves are frequent.** The game saves every thirty seconds and when it closes, and the dedicated host on its console's
  `save` and when it stops, so a crash or a power cut meets a save more often than one save's short window suggests,
  and closing the game is the one moment a save always runs.
- **The documents promised otherwise.** ARCHITECTURE §6 says every file is written to a `.part` and moved into place,
  and `WorldSave`'s own summary adds "so a crash mid-write leaves the previous save intact". It does not.

## What this slice promises

1. **The whole previous save, or the whole new one.** A save interrupted at any point, by a crash, by the process being
   killed, or by the power failing, leaves a world folder that the next load reads as either the save before it or the
   save being made, entirely: never a mixture of the two, never a world file missing, and never a thing both carried
   and lying.
2. **A record marks the moment.** A save writes every file it changes beside its target first, each flushed to the
   disk; then writes a record of what it will put in place and what it will remove, `save.commit`, beside itself,
   flushed, and moves it in whole; then puts the files in place and removes what emptied; then removes the record.
   Until the record is in place the previous save stands untouched, and once it is, the new save is the one read.
3. **Recovery on the way in.** Reading a world folder first finishes a save whose record is in place, putting in place
   what was not yet and removing what should go, or clears away the files of a save that never placed its record. A
   file the record names whose bytes are not the bytes the record says is refused with its name, and never read as the
   world.
4. **Every way in.** The host's continue, the game's preparation and the menu's newest world all see a folder part way
   through a save as the world it is.
5. **Proved by interrupting it.** Tests stop a save after each of its steps in turn, on a world where since the last save
   a founder picked a thing up, a thing crossed a cell's edge and a cell emptied, and hold that every folder then reads
   as one save or the other, whole, with nothing left over; that a replacement file cut short before the record is in
   place leaves the previous save; and that a folder whose record names a damaged file is refused.
6. **The documents say what is true.** ARCHITECTURE §6 and §10 describe the record and the recovery, `WorldSave`'s summary
   says what a crash leaves, and `save_check.py` refuses a folder at rest that holds a `.part` or a `save.commit`.

## Non-goals

Earlier saves to return to (a backup, or several); saving on a worker thread, and a save's cost in the frame; what the
world remembers of what a founder changed (the animals' disturbance, what was used up); a disk that loses what it said
it had written; two servers writing one folder.

## How it is proved

`dotnet test` and the Unity-layer compile, the count as run; `python Tools/unity/editmode.py`; `save_check.py` on the gate
world, green.

## Exit record (2026-09-13)

**What exists.** `WorldSave.Write` writes a save's files aside and flushed, places `save.commit`, puts the files in place
and removes what emptied, then removes the record; `WorldSave.Recover` finishes a save whose record was placed and clears
one whose record was not, and `Read` and every `Write` run it first; `WorldSave.Exists` and the game's menu count a
folder holding the record as a world; `eg2.save_commit`, version 1 (ARCHITECTURE §10); `save_check.py`'s first row; the
host's log gives each save's time; and the M1.3b gate. Nothing a player sees changes, except that an interrupted save
no longer loses the world or gets it refused, and that a save now takes longer (below).

**Tested, and how.**

- `dotnet test`: 464 passed. `SaveInterruptionTests` stops a save after each of its steps in turn, from the first file
  written aside to the record's removal, on a world where since its last save a founder picked a thing up, a thing
  crossed a cell's edge, a cell emptied and a thing was set down where nothing lay: by the world's digest, every stopped
  folder read as the save before it until the record was placed and as the save being made from then on, with nothing
  left over. A replacement cut short before the record leaves the save before; a damaged file the record names is
  refused with its name; and a world whose first save stopped after its record is still a world, and reads as that save.
- Each test's reason was broken once, the tests went red, and the code was put back: each file put in place as it was
  written, before the record; a world read without recovering its folder; a folder holding only the record not counted
  a world; the record's checksums not held.
- The Unity-layer compile: 0 warnings, 0 errors. Edit-mode: 8 of 8.
- The gate world, saved before this slice by the old code, was continued and saved again by the server host under the
  new one (`populate.py`): `save_check.py` green on every row, the folder one whole save. The host's saves of it took
  258.7 ms, the first in a fresh process, then 51.9 and 32.4 ms.

**Not exercised, or not holding.**

- No process was killed and no power was cut. A crash is stood for by an exception thrown after a step, after which
  nothing of the save runs, and a torn write by a file cut short; that the disk keeps what a flush handed it is the
  disk's.
- A replacement damaged after the record was placed refuses the world, where a second copy would let it go back to the
  save before; keeping one is a non-goal.
- Once the record is placed the files go into place one after another, so another program reading the folder in those
  moments could see old files and new together. Only the server reads the folder, and it recovers before it reads.
- A save now pauses the game. The game saves on its main thread every thirty seconds and when it closes, and flushing
  each file is most of the host's times above, where a frame at sixty a second is 16.7 ms. The pause in the built game
  was not measured (DEBTS).
